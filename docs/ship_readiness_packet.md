# Broono Ship Readiness Packet

## Release Verdict

**Conditional ship after external launch checklist is completed.**

The repo-level blockers called out in the ship-readiness plan are now addressed:

- Email verification no longer auto-completes onboarding.
- Free users keep access to the app shell, profile, sign-out, and delete-account.
- Production state no longer ships with seeded demo health data.
- The third-party news proxy has been removed from the shipped experience.
- User-facing mojibake in the primary app flows has been cleaned up.
- Auth send, verify, delete, and gated-flow behavior now have automated coverage.

## What Changed

### Product and UX

- First successful verification now lands users in onboarding.
- Free users can complete onboarding and use core tracking without being trapped in a full-screen paywall.
- The paywall now appears at feature gates:
  - Progress tab
  - journal usage limit
  - export data action
- The updates tab is now a launch-safe placeholder while a first-party news pipeline is built.

### App State and Privacy

- Persisted store defaults are now empty for logs and journal history.
- Persisted store migration resets old pre-launch onboarding/demo state.
- Account deletion now resets local persisted data instead of only clearing auth fields.
- Browser account deletion now works cross-origin because backend CORS allows `DELETE`.

### Backend and Operational Hardening

- Magic-link requests now normalize email addresses before storage and verification.
- Magic-link creation now has a best-effort in-memory rate limit for repeated attempts from the same client.
- Backend tests now cover:
  - send magic link
  - rate limiting
  - verify flow
  - delete-account
  - RTDN status mapping

## Manual Launch Checklist

These actions remain external to the repo and must be completed before production release.

### Cloudflare

- Set Worker secrets and vars:
  - `JWT_SECRET`
  - `RESEND_API_KEY`
  - `STRIPE_SECRET_KEY`
  - `STRIPE_WEBHOOK_SECRET`
  - `STRIPE_PRO_PRICE_ID`
  - `GOOGLE_PLAY_PACKAGE_NAME`
  - `GOOGLE_PLAY_SERVICE_ACCOUNT_KEY`
  - `GOOGLE_PLAY_WEBHOOK_TOKEN`
  - `GOOGLE_CLIENT_ID`
  - `GOOGLE_ANDROID_CLIENT_ID`
  - `FRONTEND_URL`
- Verify D1 schema includes `google_play_token`.
- Confirm production CORS origin matches the final frontend URL.

### Resend

- Verify sending domain and sender identity for `login@broono.app`.
- Confirm production magic-link delivery and spam-folder behavior.

### Stripe

- Confirm production subscription product and price.
- Verify webhook delivery to `/api/stripe/webhook`.
- Validate checkout success and cancellation return flows against the live frontend URL.

### Google OAuth and Google Play

- Create or confirm web and Android OAuth clients.
- Register correct SHA-1 and SHA-256 fingerprints for debug and release/Play signing.
- Create `broono_pro_monthly` subscription, base plan, and 2-day trial offer.
- Configure RTDN Pub/Sub push to `/api/play/webhook`.
- Upload a release-signed AAB and validate internal testing installs.

### Store Submission

- Complete Play Store assets, listing copy, and screenshots.
- Complete Data Safety using the current local-only health-data architecture.
- Confirm privacy policy and account deletion posture before review submission.

## Remaining Known Risks

- Magic-link throttling is currently best-effort in-memory protection. For production, add Cloudflare-managed rate limiting or WAF rules as a stronger external control.
- The updates tab is intentionally operating without a live news feed. If live health news is required for launch, build it behind a first-party backend route before re-enabling.
- `logout()` still signs the user out without wiping local health data. This is acceptable for a single-user device model, but multi-user shared-device handling should be reviewed before broader rollout.
